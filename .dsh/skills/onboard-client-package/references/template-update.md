# 在现有客户包内更新模板

## 入口与边界

用户说“更新模板”“现有客户换模板”“在这个包内加新版模板”时，使用本流程，**跳过主手册建包骨架阶段**。沿用现有 package、manifest、角色和能力配置；先读取原文件，不覆盖成新包示例，不删包、不重建包、不重置提示词。

“模板更新”分两种状态：

- 本次模板仍未确认：直接接手本次 task_id，按 [未确认模板优化与交接](template-refinement.md) 继续，不重复建任务。
- 原模板已经确认，用户明确要求更新模板：旧模板保持只读，在**同一客户包**下建立本次更新的独立比对任务，产出新的未确认模板；不得改旧 confirmed 工件或旧任务的 confirmed_template_ref。新任务是用户明确要求的模板更新，不是原候选优化失败后的绕过手段。

仅有“继续建包”“优化一下”的指令不能自动当作替换已确认模板的授权。不能判明目标客户、更新对象或本次候选时，先按现有材料查证，仍缺信息才集中问两三个问题。不因本流程另建客户包、迁移客户数据或重启服务。

## 1. 盘点并记录旧基准

1. 核实现有包可用，读取主手册 10.2 的包识别检查及 `check_package.py --package <现有包>`；若现有包损坏，报告具体问题，不建一个新包来掩盖。
2. 带 `X-Report-Package` 读取模板列表，定位用户指定的旧模板 task_id/ref，读取其定义和工件健康状态。不得取全局最新、仅按同名或把内置候选当旧确认模板。记录旧 task_id、confirmed_template_ref、名称、健康状态及其只读内容哈希；保留更新前客户包文件的差异基准。
3. 读取现有模板的字段、固定文字、规则、图表、writer_schema，以及包内 prompts、writer_slots、calculations、vocabulary、数据契约。明确本次变更来自新版历史报告、版式、字段、口径或写作要求；客户/角色/功能没有变化的部分继续沿用。
4. 已有报告仍引用原 `template_ref`，不自动改写其任务、参数、草稿或文件。旧模板缺文件/不可读须作为既有问题单列，不能声称它可回退或可复用；在无法读取旧基准时标记兼容性未验证。

## 2. 在原客户包创建或接手本次未确认模板

用户在“02 模板确认 → 新建比对任务”选择**原客户包**，上传至少两份内容不同、能体现目标模板的历史报告，第一份作排版基准；命名建议包含用途与更新日期，便于识别，新旧名称不同不代表模板引用已自动切换。报告不足则说明材料缺口，不能伪造第二份或降低门槛。

若已有本次未确认任务，就使用该任务，不再创建；新建时记录创建响应/页面地址中的 task_id。上传、任务请求、后续读取都绑定同一现有包，请求体 package 若存在须与请求头一致。不复用旧比对操作的幂等键来创建新任务，避免误取旧任务。

用户完成比对与人工修改后，**先不确认**，通知 agent 接手。四项处理功能先逐项核对用户决定；缺失或变动项按每轮两三个问题询问，不把旧模板或界面默认值当成本次授权。选择后点击「保存处理规则」，关闭重开核对一致，模板仍未确认。尚未独立保存的图表选择交给 agent 核对并通过当前候选接口保存，不为保存选择而提前确认。

交接提示应明确：

> 请在现有客户下创建本次模板比对，修改后先不要确认。完成后告诉我，我会读取 LLM 审核意见并优化这份新候选。原来已确认的模板和已有报告会保留。

## 3. agent 优化本次候选并对比变化

执行 [执行闭环与交接检查](execution-gates.md)：为本次候选建立台账，对模型意见、业务问题及agent发现的历史差异逐项给实际下一动作。能沿用的用户决定直接落实；需要新取舍的当轮集中询问，不能只加“待处理”提示后交付。

完整执行 [未确认模板优化与交接](template-refinement.md)：读取 LLM 的实际 human_review_items、用户草稿和原文证据，通过现有支持接口修改本次同一未确认任务，保存后重新读生效预览。记录 candidate_ref/revision 的变化；不修改旧确认版本，不清空人工草稿，不伪造 validation。

额外形成新旧差异表：章节/固定文字、字段增删改、字段归属与取数绑定、规则与功能开关、图表、writer_schema。每项注明变化依据、是否需同步包配置/提示词及对旧模板后续使用的影响。没有证据的业务口径问用户，不把模型建议直接当业务事实。

接口不支持的结构修改明确列缺口；不借“更新模板”绕过未确认编辑限制，不手写数据库或工件来强行通过。

## 4. 用户审阅并亲自确认

先运行 `check_review_gate.py --require-ready`，确认返回0，才交付本次预览、LLM意见处理清单和新旧差异，等待用户审阅。开放项须继续修复、提问或开发交接，不能带“未处理项”引导最终确认。**由用户亲自点击“确认并保存模板”并通知agent**；agent不代点、不调用confirm。

收到通知后按主手册 1.5.5 检查本次新 task_id 的 confirmed + available、来源、comparison_ref 和 writer_schema，记录新 confirmed_template_ref，同时只读核实旧模板引用与内容未被改变。若用户未通知，或通知了但物证不成立，都不能先改提示词。

此后新旧已确认模板均只读；不通过 chart-version 或再次确认来继续优化本次版本，不删除旧模板，不重绑已有报告。没有单独指定的默认切换机制，不虚构“最新模板自动生效”。

## 5. 按差异同步提示词与包配置

确认后再检查哪些提示词需要更新，沿用主手册 30 条必写 + 4 条条件键的需求与来源登记规则；不把新建包流程理解为全部重新写一遍。没有受影响的正文保留并登记依据，保留 index 中其它有效声明、角色和条件键。

writer_slots、calculations 或图表声明确需同步时，只改有证据的差异，不把新 writer_schema 直接覆盖成“包内唯一模板”的假设。配置中的字段匹配与旧模板兼容性须逐项核查。

**同包共享影响**：当前提示词与部分客户包配置按包解析，并不随每份 confirmed 模板自动封存成独立副本。已保存报告的模板引用不会自动变更，但旧模板今后新建/重新生成报告时可能读取更新后的提示词或配置；不能承诺旧模板以后生成行为完全不变。

优先让提示词按实际字段语义/schema 兼容新旧模板，避免写死某份模板的字段 id、期号或业务事实。若新旧要求互斥、现有配置无法兼容，先展示具体冲突和影响，取得用户对取舍的决定后再写冲突部分；不能私自废弃旧模板、另建包或声称系统已有模板级提示词版本隔离。独立保存修改前文件和差异用于人工评估回退，不自动回退其他并发修改。

## 6. 技术自检 → 用户业务测试

- 按主手册第十章做包契约、声明集合、来源、字节口径和定向隔离回归。对本次修改范围选择测试，不运行全量 pytest，不改门禁基线；只改客户包时核对 core/app 字节不变。
- 只读核验旧、新模板仍在目标包内，旧 ref/内容未改，本次新 ref 健康，已有报告未被重绑；未有足够数据验证的项标记“未验证”。
- 交用户明确的“现有客户 → 本次新模板名称及任务 → 数据输入 → 生成步骤 → 观察点”测试指引。建议覆盖新模板，并在共用提示词/配置变更时补测旧模板；业务测试由用户亲自执行，agent 不自动出稿或调用模型。
- 状态区分“候选待审阅”“待用户亲自确认”“待用户测试”“用户已验收”。技术自检通过不等于用户验收。用户提供本次任务与反馈后，agent 只读分析、按反馈修改获准的提示词/配置，再交用户复测；不改已确认模板或另换确认版本。

## 更新记录

在现有包 `接入记录.md` 追加“模板更新”段，或准备 `模板更新记录-<日期>.md`；不得覆盖旧接入证据。至少记录：

| 项目 | 内容 |
|---|---|
| 身份与基准 | package、旧 task_id/ref/内容哈希、本次新 task_id/ref、来源报告 |
| 优化与确认 | LLM 意见处理、用户修改保留、新旧差异、用户亲自确认通知及物证 |
| 包内变更 | 提示词/配置的修改前基准与差异、沿用依据、共用影响与兼容限制 |
| 校验与验收 | 技术检查原始输出、用户测试指引、实际测试任务/结果、未验证项 |

记录名称可含日期，确认版本与客户包 version 不能因记录命名自动递增或重置；现有 manifest 版本规则若无明确约定，不擅自更改。

模板更新也必须执行 [数据字段绑定检查](data-binding-readiness.md)。新旧字段逐项比较，已有目录能力由 agent 配好；缺工具先询问具体开发授权。旧确认版本保持不动，不以运行时规划器兜底作为交付依据。


提示词更新后必须执行主手册「提示词卡片与适配记录」要求：为已核查兼容的确认模板 ID 写入 `prompts/adaptation.json` 的有效摘要与真实时间。新模板仅确认、提示词尚未更新时记 `pending`；不能凭旧 V2/V3 文件或修改时间登记已适配。共用提示词变更后，旧模板须重新核查后才更新适配记录。

模板确认前还必须执行 [字段关联与实际请求核验](writing-groups.md)，交付关联组并检查实际请求，不以描述或提示词代替上下文传递。
