# 模板优化的执行闭环与交接检查

适用于新客户建包和现有客户模板更新的阶段2。维护skill本身、单次只读答疑不要求创建客户台账。这里定义每一步的实际产物与继续条件；“文档已经要求过”或“页面已加待处理提示”不能替代执行。

## 接手后的固定产物

在原客户包准备 `template-review-ledger.json`，保留原接入记录；证据正文可放同包的模板更新记录。不把客户材料写进skill。

1. 读取本次任务、生效候选及人工草稿、全部模型意见与业务问题、指定历史报告。保存 package/task_id/candidate_ref/draft_ref，不能用全局最新任务代替。
2. 对照历史正文形成覆盖清单：章节；列表数量与编号；可选内容；数据绑定；字段关联；真实写作请求；预览与导出；共享包配置兼容性。
3. 合并重复业务决策，但台账仍逐一关联原意见ID。例如“多于10类”和“少于10类”可合并问一次动态列表方案，修复后两条原意见分别回填证据。
4. 每项进入下表中的一个分支。不能停在一句“待处理”，也不能把任务转交给用户自己查代码或接口。

| 可观察条件 | agent下一步 | 完成证据 |
|---|---|---|
| 历史材料、用户决定和现有能力足以确定 | 在授权范围内直接修复，不重复问已回答问题 | 正式接口保存、重新读取生效值、相应技术检查 |
| 有业务取舍，当前材料与历史决定仍不足 | 当轮集中问2～3个问题，给问题、证据、选项、影响；记录已实际发出的问法 | 用户实际答案 → 保存决定 → 实现 → 重读与验证 |
| 多条意见对应同一个问题 | 合并提问并保留原意见映射 | 一项决定解决多个意见，但每条均有处理记录 |
| 缺计算、图表或结构编辑能力 | 说明具体缺口、现有入口为何不足、通用扩展和影响；按工具交接规范落文档并核对已有授权 | 有授权则推进具体实现；交其他实现者时给可执行交接，不自动派agent |
| 建议不适用、与来源或既有决定冲突 | 给出不采纳理由和依据；确有新业务冲突才问用户 | 可核查的依据及“不采纳”处理记录；不是静默忽略 |

用户只答部分时，落实已决定且不依赖未决答案的事项；未答项保留明确问题。等待答案不等于允许推断授权。发现接口能力不足时不手改工件、数据库、validation或确认状态。

## 台账状态必须能驱动下一动作

`issues` 的 `kind` 为 opinion/business/finding；原意见和业务问题ID取本次API，agent额外发现的问题用稳定本地ID。不要漏掉“模型没提但历史对照已发现”的问题。

| status | 记录内容 | 下一步 |
|---|---|---|
| open | 已发现问题 | 填具体next_action并立即推进 |
| awaiting_user | 实际问题、证据和选项；已问/未问如实记录 | 发出问题或等真实回答，收到后转实现 |
| awaiting_implementation | 缺口文档、授权/交接范围和明确实现任务 | 实现或等待用户指定的实现者，不伪称完成 |
| in_progress | 正在执行的修改/核查 | 完成保存与验证 |
| verified | decision_basis、实际保存和非空证据文件 | 可进入交接检查 |
| not_adopted | 有依据的不采纳理由及证据文件 | 视为已核对；展示“不采纳”，不能声称“已修复” |

开放项的 `next_action.kind` 取 ask_user/implement/handoff_extension/verify；ask_user须给实际 `question`，其它须给具体 `description`。可增加用户回答、问题批次、负责人和验证命令等记录。存在开放项时，回复应是具体提问、明确开发交接或局部结果加下一动作；不能以“未处理项已列出”收尾并邀请确认。

## 历史报告对照与字段关联

逐节检查，不能把“有四组案例”当作整个模板关联已完成：

- 标题—事件经过—分析建议：同一个案例，分组间避免重复；数量随历史体例和用户决定，不写死三组或四组。
- 分类列表—计数/占比—举例—总体研判：共享确认统计与类别材料，核对历史列表真实数量，不能沿用模型默认4～6项。
- 峰值日期—事件：必须按同一统计范围算出日期，并用该日期取材料；仅写“同题”不等于已实现动态查询。
- 平台列表—来源说明、媒体家数—报道数—示例：同口径；纯数据字段用绑定和计算约束，不为显示组标识改成writer。
- 媒体/网民话题—各自举例：区分材料来源与调性，不能把正面状态字段拉入只查负面的组。
- 新增正面案例、可选段落：必须有真实正文块、字段、Schema与版式位置，不能只答“保留”而正文不存在。
- 前瞻：共享次月窗口与研究依据，但保留前瞻研究、条数和引用校验链路；普通关联组是否绕过角色检查由实际请求验证。

在 `coverage` 中逐项记录 verified/not_applicable/open、reason和证据文件。not_applicable要说明本模板为何不存在该关系，不能用来隐藏已发现的缺口。八个area名称见脚本 `AREAS`。固定月份、历史事件和数量是证据，不能直接升为所有客户的规则。

界面核查分两步：先读API实际members，再检查界面。未勾选的月份字段若只是备选列表，不应改动后台成员；默认已关联成员与折叠备选需分清。验证正文编号、关联标识、组成员、重开保留；接口200或有组名不代表UI和写作已正确。

## 当前受支持的保存入口

写入前核实本机源码与已部署服务能力，不假设旧服务支持新参数；保存后必须重读字段、块与Schema，不能只检查HTTP200。

- `/definition`：`writing_groups`保存关联；`rules`保存四项用户选择。保持本次package、task_id与最新expected_revision。
- `/definition` 的 `structural_changes`：`reason`、`field_updates`、`insertions`。见 `app/template_structure_edits.py` 的严格模型。仅修改未绑定writer字段的允许属性；插入段落须锚定已登记来源报告中的真实段落，校验来源哈希、固定前缀和样式锚点，不接受任意模板替换。
- 动态类别列表：以已决定口径配置 `category_coverage_scope`，核对实际writer请求是否携带所有非零类别、统计与逐类材料，并校验覆盖数量和顺序；取消固定条数上限不等于已保证全覆盖。
- 独立可选段：字段optional、output_schema.required、writer分配与导出省略一致。分别验证“有第5条”“只有4条”；空内容不能留下“五是”，也不能把数组塞进首字段。条数以客户决定为准，不把4～5条固化为所有客户要求。
- 人工草稿存在时结构保存应重放其选区与field_edits；重读 `/draft` 确认修改未丢，旧草稿冲突不可绕过。

## 意见处理状态的真实回填

用 `/agent-review` 保存 expected_revision + entries。opinion的ID取 `agent_review_status.opinions.items`，business的ID取相应business条目；status取 addressed/pending/needs_user，给note和evidence，业务决定填写真实answer。后端 `addressed` 表示已完成核对，若不采纳必须在note说明，不代表用户已确认模板。

只有修改已保存、重读与验证通过后，才把相应项置addressed；不能先让界面变绿再做修改。修改候选后旧处理记录会过期，需重新核查再回填。保留原意见，补充定位至合并后字段，不因原字段消失便认定问题消失。

检查“模型终审参考意见”与“业务问题处理结果”的醒目数量、逐项说明、用户答案和重开保留。两栏全部完成不代表agent额外发现的问题也已解决，仍须过下述台账检查。业务问题预填答案后仍由用户亲自确认模板。

## 确认前必须运行的只读检查

准备台账结构（只填真实结果，不复制示例冒充已核验）：

```json
{
  "package":"实际包", "task_id":"实际任务", "candidate_ref":"当前工件", "draft_ref":null,
  "feature_decisions":{"dedup":true,"classification":true,"first_warning":false,"top10":false},
  "issues":[{"kind":"opinion","id":"API中的ID","status":"awaiting_user",
    "next_action":{"kind":"ask_user","question":"实际需要用户选择的问题"}}],
  "coverage":[{"area":"history_structure","status":"open","reason":"尚在对照历史章节","evidence":["实际存在的核查记录.md"]}]
}
```

从仓库根执行（解释器按环境选择，包名、ID、台账均替换为本次真实值）：

```powershell
.conda/JJDreport/python.exe .dsh/skills/onboard-client-package/scripts/check_review_gate.py --package <包> --task-id <任务ID> --ledger packages/<包>/template-review-ledger.json --require-ready
```

- 脚本只GET任务/定义/草稿、读取本地台账和证据文件，不写状态、不调用模型、不确认模板。可以去掉 `--require-ready` 查看下一动作，但不得据此跳过正式交接检查。
- `--require-ready`仅在 `ready_for_user_confirmation=true` 时返回0；身份不符、候选/草稿过期、未明确四项选择、待绑定数据字段、遗漏或未处理意见、开放历史发现、缺覆盖项/证据文件均返回2。
- 返回2时按具体错误继续修复或提问；不是把脚本失败改写成“检查已完成”。正在等待真实答案时可以交局部结果，但状态必须为待决定，不能邀请最终确认。
- 脚本验证当前身份、完成记录和证据文件存在性，不能判断证据内容真假或保证报告业务质量。agent仍须阅读证据并执行相应检查；不得创建空文件或重复无关文件凑齐覆盖项。
- 返回0后才能交“变更/未采纳理由 + 实际预览位置 + 技术验证 + 等你审阅并亲自确认”。收到用户完成通知，再走主手册确认物证与提示词适配检查；不自动确认或试跑业务报告。

## 服务加载与工具拒绝

技术验证要区分工作区代码、临时服务和正式端口。新增参数/返回字段须在正式服务重读验证；临时服务成功只能证明新代码可运行。

一次命令被拒绝，只记录当次命令、返回原文和明确原因；没有依据不能推断新增永久禁令。用户后续明确要求解决后，按当前授权与工具规则重新核实状态；若允许重启，先核对没有业务任务运行、监听进程属于本项目，再隐藏启动并验证HTTP与目标功能。不换工具绕过拒绝，不中断在跑的业务任务。仍被拒绝时如实交代具体未加载部分，不反复以一句“之前被拒绝”替代当前查证。


## 本轮新增的防漏检查

模板复核遇到同一数据同时存在原始记录、去重事件和全量统计时，必须在字段或关联组保存 `scope` 与 `count_unit`；实际 writer 请求、双审请求、预览和导出必须读取同一声明，禁止只在提示词中描述口径。

正面材料表必须保存本地选题条件和空结果行为；不允许因筛选为空静默回退全量。类别动态列表必须以程序返回的全部非零类别为 schema 长度，图表和正文共用同一单位。

新增结构前先记录来源段落和前值 parts；固定文字、可选段、字段绑定和图表口径只能通过受前值约束的结构补丁保存。可选组的字段必须整体省略或整体出现，并在审核、浏览器预览、Word 导出三处一致。

从已确认模板更新时，必须新建同包“未确认修订候选”，保存来源模板引用、来源哈希、修订理由和幂等键；不得修改旧确认工件，不得伪造模型研判已重新运行。
