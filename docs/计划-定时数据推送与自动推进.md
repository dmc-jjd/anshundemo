# 计划：定时数据推送 + 自动跑到人工研判节点

> 状态：**已登记，未排期**。用户明确「只是有这个需求安排，还没确定数据端口推送的格式，可以先写入计划」。
> 记录日期：2026-11-16。本文只固化需求与设计约束，**不含实施任务分解**——等数据端格式确定后再拆。

## 一、需求（用户原话）

> 未来可能每个客户都有一个固定的数据接口，数据端会根据报告要求按固定时间进行数据推送。
> 我们的这个程序在服务器上长期在线，当定时数据流路由过来以后，自动执行报告的前期数据处理 + 填写工作，
> 在核对数据的人工研判节点暂停。

拆成四句：

1. **每个客户一个固定数据接口**（不是所有客户共用一个入口）
2. **数据端按固定时间推送**（推模式，不是我们去拉）
3. **程序长期在线**（服务常驻，不是一次性的 CLI 跑批）
4. **自动跑前期处理 + 填写，在人工研判节点暂停**

## 二、与现有架构的关系

这条需求**正好落在多包架构之上**——推送过来的第一件事就是「这是哪个客户的数据」，
而 M1（解析层按包）/ M2（数据隔离 + 注册表）解决的正是这个问题：

```
数据推送 → 识别客户包 → 用该包的 manifest/template.json/prompts 跑
         → 产物写进 data/packages/<pkg>/
```

暂停点是现成的：`awaiting_review`（等待整体数据审核）就是「核对数据的人工研判节点」。
所以要新增的不是暂停机制，而是**「建完任务自动推进到那一步」的触发**。

## 三、未确定项（阻塞排期，等用户/数据端给答案）

| # | 待定 | 影响 |
|---|---|---|
| 1 | **推送的数据格式**：Excel/CSV 文件？JSON 记录数组？还是只推「数据就绪」通知由我们去拉？ | 决定接收端解析路径与校验强度 |
| 2 | **推送频率**：每月一次？每周？还是不定时？ | 决定幂等键（按「客户+期号」还是「客户+推送时间」） |
| 3 | **鉴权方式**：固定 token？按客户分 key？IP 白名单？ | 决定接口设计与密钥管理 |
| 4 | **失败语义**：推过来但数据不合格，返回 4xx 让数据端重推，还是收下后进人工研判？ | 决定接口是否承担校验职责 |
| 5 | **是否允许人工触发重跑**：推送失败/需要更正时，是否要能手动重放某次推送 | 决定是否保留推送原文 |

## 四、需要新建的三个能力（等上面定了一部分再细化）

### ① 接收端点
现状只有人工上传（`POST /api/files` + 建任务），**没有「第三方推过来」的入口**。

大致形态（供讨论，未定）：
```
POST /api/ingest/{package}
  鉴权：按待定 §3
  载荷：按待定 §1
  行为：落文件/记录 → 幂等判重 → 建 report task → 自动 resume 到 awaiting_review
  返回：{ task_id, phase:'awaiting_review' } 或明确的 4xx（数据不合格）
```

### ② 幂等（重复推送不能建两个任务）
已有 `idempotent(key, value, package=…)` 基建（M2 已按包路由），但**没用在推送场景**。

需要定幂等键，例如：
```
(package, report_month, issue_number)      ← 若数据里带期号
或 (package, payload_sha256)                ← 若不带期号、只能按内容去重
```

### ③ 自动推进
建完任务后要自动跑到 `awaiting_review` 并停下。

现状：建任务是同步的、图是后台跑的（`app/workflow.py` 三个后台图入口，M2 已让它们在任务所属包的 ContextVar 里跑）。

需要确认的：**新任务是否自动开跑**（现在是建完等人工点「按新规则重新处理」），
以及**跑完后如何通知人**（企业微信/邮件/站内待办？待定）。

## 五、前置条件

```
① 多包架构 M2 完成（数据隔离 + 注册表）        ← 已完成并提交（c32311a）
② 多包 M3 完成（前端选客户 + store 旧面按包）   ← 未开始
③ 真实 data/ 迁移 + 8765 重启                  ← 未执行
④ 推送格式确定                                  ← 等数据端
```

**②③ 是硬前置**：M3 不做完，B 客户的 docx 列表/编辑页会查 A 的库；
真实数据不迁移，推送写进去的产物和现有产物不在同一个根。

## 六、为什么不在多包架构同一批里做

- 它是**新功能**（新增对外接口 + 常驻调度语义），不是多包架构的一部分
- 混进同一批会把风险放大：多包改造已经动了 30+ 文件、三个基线，再加对外接口会难以定位问题
- 而且格式未定，写了大概率返工

## 七、刻意不做的设计决定（留给排期时讨论）

- **不做定时器**：数据端推，我们不主动拉，所以不需要 cron/调度器。除非 §1 答案是「我们去拉」。
- **不做队列**：如果推送频率是月级，一个请求同步跑完前期处理可接受；若变成高频，才需要队列。
  （前期处理本身可能几分钟：去重 + 研判 + 写作，同步等会不会超时？这是排期时要量的事。）
- **不新造暂停机制**：复用 `awaiting_review`，不引入第二种人工节点。
