# 结构化模板与 JSON Schema

## 模板创建的前置流程

1. 上传两份及以上不同的可读 DOCX，拒绝内容相同的重复文件。第一份为排版基准，其他报告均参与比对和模型语义分析。
2. 本地解析正文与表格，保留文件 SHA-256 和块位置，生成跨报告比对和本地模板假设。
3. 模型输入包括制定规则、所有历史报告的完整可提取正文/表格、本地比对、本地模板候选及可用数据绑定目录。快照保存为 `template_model_input`，不含密钥。
4. 模板 Agent 按完整语义重新划分固定文字、列表、完整事件标题、分析段和统计字段。每批处理3个完整基准块，每批仍提供全部报告上下文；输出完整块及字段结构，禁止只返回摘要。
5. 程序检查每个来源片段、原文逐字重建、全部报告块覆盖、字段引用/所有权和绑定目录，生成新候选与 JSON Schema。失败进入 `template_review_failed`，不能进入人工确认；重试可复用同输入已验证批次。
6. 人工查看模型后模板、本地初稿和全部来源，处理具体业务问题，再整体确认。确认绑定候选引用、修订、输入哈希、制定规则版本和校验记录；旧的弱研判候选必须重新研判。已确认版本保持不可变。

相同原文只说明这两份报告中相同，不能自动证明以后每个月都固定。对齐不明确的块、字段含义与统计口径保留待审。模板定义里的历史值用于解释槽位，不作为本月事实。

## 写作与输出

报告处理时显式选择确认后的模板版本。数据处理 Agent 接收该模板的字段目标；Writer 接收该模板的文字字段、固定文字结构和本月记录证据，返回字段对象，不返回整段自由正文。

- `output_schema`：完整输出约束，所有字段必填，拒绝未知字段。
- `writer_schema`：只包含 Writer 拥有的文字字段，拒绝数据字段。
- 每个填写值带 `source_refs`，程序检查引用是否属于提供的证据。
- 数据字段通过明确的工具结果路径绑定；未配置绑定则保留缺失，不猜测数值。例：`{"tool":"calculate_metrics","path":["record_count"]}`。
- 表格字段定义为行数组，每行列数与来源表头一致。
- 工作建议编译为1—5条的可变字符串列表，按条目生成独立Word段落，不固定历史3条或4条；历史建议段全部替换，避免重复或漏掉条目。
- Word 渲染使用第一份源报告作为版式来源，按字段结构拼装固定文字和填写值。未填字段、未对齐块、旧图表均显示显式占位符，避免沿用历史数据。

当前结构化输出为预览状态；尚有未填数据绑定、图表和审查问题时不能当作终稿。

## 检查与修改候选

`GET /api/templates/{task_id}/definition` 返回候选定义、来源、两个 Schema 和修订号。

`PUT /api/templates/{task_id}/definition` 接受 `expected_revision` 与按字段 ID 编排的 `fields` 修改对象，当前允许修改显示名称和配置已支持的业务规则。语义、绑定与字段 Schema 的变更必须重新研判，不能伪装成已通过模型审查的版本。

确认入口 `POST /api/templates/{task_id}/confirm` 需要 `expected_revision`、`candidate_ref`、`rules` 与具体未决项的 `resolutions`。报告页面可选择确认后的结构化版本；8 月基准模板保留为历史预览路径。

## 实际样本与验证

此前的本地弱研判候选使用真实6、7月报告，产物为：

- `data/structured-template-review.json`
- `data/structured-template-writer.schema.json`

旧候选有123个字段，其中Writer字段79个；它不代表新的模型语义模板。新一轮真实6、7、8月任务ID保存于 `data/current-template-task.txt`；运行输入、逐批模型结果、候选及校验记录均在工件中留存。10月继续保留为独立生成验收材料，不作为这轮建模输入。

模板提示词与规则在 `app/template_review.py`，类型契约在 `app/state.py`；运行数据仍放 `data/artifacts/`，不写进 Python 代码文件。

## 三轮纠正与异常研判

`template_validation.py`集中收集多项问题，`template_execution.py`每批最多三轮并保存每轮输入、候选、问题、模型调用/校验/本轮耗时。失败批次达到上限后进入`template_manual_review`，不允许直接确认或用通用审阅按钮跳过；异常编辑器提交后仍须通过相同校验。已通过批次及人工修正检查点保留。合并时如发现跨批次问题，同样限次纠正后再交人。

`timing.py`与Store共同记录所有任务阶段边界，区分自动处理、人工等待和等待重试。页面实时计时且刷新后保留，确认后停止对应任务计时。历史任务缺失的阶段不会补造耗时。
