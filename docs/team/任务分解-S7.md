### G-CORE-ISO｜S7 核心门禁：基座的「身份」与「方向」三判据

**存在理由**：P7 的判据是「只加包、不动基座」，而 S2–S6 的门禁里**没有任何一条钉住 `core/` 的字节身份**——
`G-CORE-CLEAN` 只查 5 个业务词，`G-PYTEST` 只查行为，`G-SPECS`/`G-GRAPH` 只查特定契约。
所以「加了一个包、core 没动」这句话今天**无法被机械判定**；而「core 不依赖 app」这句话今天是**假的**（15 处）。

```powershell
& $py scripts/gate_core_iso.py --check --baseline docs/team/baseline/core-S7-preB.json
```

**三个判据（都应逐行打印，便于归因）**

| 代号 | 算法 | 抓什么 |
|---|---|---|
| **CORE-HASH** | 遍历 `core/**`（含 `.py`/`.json`；**排除** `__pycache__`），按 posix 相对路径排序，对 `f'{rel}\0{sha256(bytes)}\n'` 逐行拼接后取 `sha256` | 基座**任何**文件被加/删/改 |
| **CORE-FILES** | 上述文件数 | 27 →（WP-B 后）**31** |
| **CORE-DEP** | `ast` 扫 `core/**/*.py` 的 `Import`/`ImportFrom`，命中 `app` 或 `app.*` 的站点数 / 文件数 | 方向正确性；**S7 出口必须为 0** |
| **APP-HASH** | 同 `CORE-HASH` 口径，但扫 `app/**` | 宿主零改动（`--with-app` 才输出；给 §4.2 判据 Z1' 用） |

**两份基线，各自只录一次（反自证纪律）**

| 文件 | 录制时机 | 内容 | 覆盖政策 |
|---|---|---|---|
| `docs/team/baseline/core-S7-start.json` | **WP-S7-A**，任何 S7 代码改动之前 | `CORE-HASH` + `CORE-FILES=27` + `CORE-DEP` 的 15 条逐点清单 +（`--with-app`）`APP-HASH` | 录后只读；`--record` 目标存在即拒绝（`--force` 需队长书面批准） |
| `docs/team/baseline/core-S7-preB.json` | **WP-S7-B 最后一步**（`CORE-DEP=0` 且六组门禁全绿之后） | `CORE-HASH` + `CORE-FILES=31` + `CORE-DEP=0` + `APP-HASH`（`--with-app`） | 同上；这是 WP-S7-C「加包前后相等」的唯一准绳 |

> **为什么必须两份**：一份（start）证明「债是真的」，一份（preB）证明「加包没动基座」。
> 若只留一份并在 WP-B 里覆盖，就变成「清完债再录基线」，WP-C 的证明仍然成立但**债的规模**失去证据（等于自己给自己打分）。

**实现约束（写进 WP-S7-A）**

1. 脚本**只允许** stdlib（`argparse`/`ast`/`hashlib`/`json`/`pathlib`/`sys`）+ **不得 import `app` 或 `core`**——否则脚本自己会把包配置拉进来（`app/__init__.py` 的 4 个 `configure`），失去「对未配置的 core 做静态判定」的能力。
2. `--record` / `--check`（默认）/ `--twice` / `--with-app` / `--baseline <path>` / `--expect-dep-zero` 六个开关；退出码 0/1/2。
3. 差异打印**逐判据**（CORE-HASH / CORE-DEP 分开；CORE-DEP 打印 `file:line module`）。
4. `--expect-dep-zero` 在 `CORE-DEP>0` 时 FAIL（WP-S7-D 用它做出口判定）。
5. 扫描函数必须接受 `root: Path` 参数（供测试在 `tmp_path` 上造负向样本，**绝不在真 `core/` 里加文件**）。
