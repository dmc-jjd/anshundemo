### 1.2 迁移铁律（10 条，每条都可用命令判定）

1. **纯搬运优先**：被搬模块进 `core/` 时**逐字复制**，不改函数体、不改签名、不改常量。
   唯一允许的编辑是 §3 表里列明的 N 处改造点。**判据**：`git diff` 对 `core/X.py` 与 `app/X.py` 旧文件应只差 import 行。
2. **薄壳必须身份相等**：`app.X.名字 is core.X.名字`（类/函数/单例），**不是**「同名但不同对象」。
   `pytest` 里 184 处 `from app.X import Y` 全靠这条。
3. **不改 `core/ports.py` 既有类型**（S1 冻结仍有效）。要扩就写 §6。
4. **不新增 `core → app` 依赖**：`CORE-DEP` 必须恒为 `0 sites / 0 files`（每层必跑）。
   搬完的模块里若还出现 `from app.…`，说明层序错了 → 停手退回上一层。
5. **层必须下降闭包**：只搬「依赖全部已在 core」的模块。违反即产生 `core → app` 反向边（见 4）。
6. **SCC 整批**：`{event_analysis, storage, tool_executor}` 三个只能同一提交内搬完。
7. **薄壳不许新增 `def`**，唯一例外是 `app/tool.py`（`tests/test_s2_shell_registry.py:30` 钉死其顶层 `def` 集合恰为
   `{get_tool_specs, get_tool_handler}` → 它**必须保留这两个转发函数**，不能退化成纯 re-export）。
8. **客户业务词零容忍**：任何一层搬完，`gate_core_clean.py` 必须 `hits 0`。不许改 `forbidden_terms.json` 降标准。
9. **每层一个 git tag**，且回退面可机械枚举（新增了哪些 `core/*.py`、改了哪些 `app/*.py`）。
10. **`packages/**` 与 `design-pages/` 0 行**；`docs/team/baseline/*` 只读（除 §1.4 明列的重录）。

## 4. 风险

### 4.1 `app/__init__.py` 的四个 configure 顺序会不会被迫改变？

**结论：行序不用改，但语义被迫收紧成一条「导入纪律」，而且 spawn 子进程已经违反它。**

现状（13 行，5 次配置）：

```python
paths.configure_data_root(DATA)          # :8
vocabulary.configure(PACKAGE_DIR)        # :9
chart_registry.configure(PACKAGE_DIR)    # :10
skill_registry.configure(PACKAGE_DIR, ROOT/'skills')  # :11
prompt_registry.configure(PACKAGE_DIR)   # :12
```

| 问题 | 实测答案 |
|---|---|
| 顺序需要改吗？ | **不需要**。5 次配置的输入只依赖 `app.config` 的 3 个常量，搬家后取值不变（`ROOT` 在 `core/config.py` 中 `parents[1]` 求值相同）。 |
| 那什么变了？ | **「谁能先 import」变了**。今天 `import app.X` 必然先跑 `app/__init__`，所以 §0.5 的 5 个模块「白拿」配置。搬家后 `import core.X` **不经过 app 包**（`core/__init__.py` 实测 0 行）→ 同一句 import 变 `RuntimeError`。 |
| 会被迫改行序吗？ | **不会**，但**任何**把 `core` 的注册表读取提前到 `app/__init__` 之前的新代码都会炸。所以要新增第 11 条铁律：**`core/` 里凡 import 期读注册表的模块（`agent` `chart_spec` `style_skill` `tool` `writer_tools`），只能由 `app/` 侧的壳在 configure 之后导入。** |
| 有现成的违反者吗？ | **有，且是热路径**：`tool_executor._run_in_process` 的 spawn 子进程。见 RISK-1。 |
| 四个 configure 会变成几个？ | 仍是 4 个 registry + 1 个 data_root = 5 次。**若 §6 D1 选「config 整体进 core」**，则 `app/__init__.py` 变成 `from core.config import …` + 同样的 5 行，行数不变。 |

### 4.2 `storage` / `state` 上移后，`Store` 的 sqlite 路径与 `data/` 怎么处理

| 项 | 现状 | 搬家后 | 判据 |
|---|---|---|---|
| `Store` 默认根 | `def __init__(self, root: Path = DATA)`（L10）——**类定义期求值** | `def __init__(self, root=None)`；函数内 `paths.data_root()` | `Store().root == app.config.DATA`（新用例） |
| `demo.sqlite3` | `self.root/'demo.sqlite3'` | **不变**（`root` 由注入值决定） | 文件仍落在 `data/demo.sqlite3` |
| `artifacts/` | `self.root/'artifacts'` + `mkdir` | **不变** | 同上 |
| `data/` 目录本身 | `app/config.py:29` import 期 `DATA.mkdir(parents=True, exist_ok=True)` | **不变**（`config` 若整体进 core，这行跟着走，行为相同） | `import app` 后 `data/` 存在 |
| 谁注入 | `app/__init__.py:8` `paths.configure_data_root(DATA)` | **同** | 已存在（S7 B3 落地），**不需要新注入点** |
| spawn 子进程 | `tool_executor.py:53` `Store(root)` **显式传 root** | **不变** —— 子进程不依赖 `data_root()`，只依赖 `core.storage` 能被 import | 子进程不需要 configure（`core.storage` 不在 §0.5 的 5 个模块里） |
| `state.py` | 121 行纯 pydantic，**零 IO、零路径** | **无影响** | 直接搬 |

**两个必须防的写坏方式**：

1. 把默认值写成 `Path('.')`/`Path.cwd()` → 测试的 `Store()` 会写到 CWD，读到空库 → **表现为「所有任务 404 / 事件为空」**，而不是报错。
   判据：`Store().root.is_absolute() and Store().root == app.config.DATA`。
2. 把 `root: Path = DATA` 改成 `root: Path = None` 后**忘了**在函数内兜底 → `Path(None)` 抛 `TypeError`。判据：G-GOLDEN 会立刻红（它大量用 `Store(tmp)`，但 `main.store` 是默认构造）。

### 4.3 26 处 `monkeypatch.setattr(app.x, …)` 会不会因模块搬家失效？（**S6 踩过的坑**）

**会，且是静默失效。** 这是本阶段最隐蔽的回归面。

**实测面**：47 个测试文件 / 19 个用 monkeypatch / **9 个文件 26 处** patch 的是将被搬走的模块
（其余 patch `app.main`(37 处) 与 `app.workflow`(3 处)，二者**不搬**，不受影响）。

| 被 patch 的模块 | 处数 | 站点（文件:行 属性） | 那行改了什么 |
|---|---:|---|---|
| `model_client` | **9** | `test_charts_and_usage:73` MODEL_URL/NAME/KEY；`test_frozen_writer:103` 同三项；`test_section_two:218` 同三项 | 屏蔽真实模型端点 |
| `historical_web` | 3 | `test_second_section_gaps:97` `request`；`test_section_two:161` MODEL_URL/MODEL_KEY | 同上 |
| `chart_spec` | 3 | `test_pause_and_polling:161,188` `DATA`；`test_s3_chart_spec:73` `DATA` | 指向 tmp 数据根 |
| `timing` | 3 | `test_pause_and_polling:64` `stamp`；`test_template_repair_timing:97,111` `stamp` | 冻结时间 |
| `historical_research` | 2 | `test_section_two:197,262` `prepare_history` | 短路历史研究 |
| `structured_writer` | 2 | `test_pause_and_polling:187` `DATA`；`test_section_two:293` `invoke_numbered_writer` | 数据根 / 短路编号写作 |
| `usage` | 2 | `test_charts_and_usage:77` MODEL_URL/MODEL_NAME | 计价归属 |

**失效机制**（以 `chart_spec.DATA` 为例）：

```text
今天：  monkeypatch.setattr(app.chart_spec,'DATA',tmp) → app.chart_spec.styles_for 运行期按模块全局找 DATA → 命中 tmp  ✅
搬家后：monkeypatch.setattr(app.chart_spec,'DATA',tmp) → 只在【壳模块】上种了一个新属性
        core.chart_spec.styles_for 仍读【自己】的全局 DATA（真 data/）              → 静默无效  ❌
```

**为什么最危险**：它**不一定报错**。`test_pause_and_polling:161` 若失效，函数会去读仓库真 `data/`：
运气好找不到文件 → 抛错（红）；运气不好找到了 → 测试**照绿**，但它测的已经不是它以为在测的东西，且可能**写脏 `data/`**。

**三种处置（按 26 处分配，逐条可判定）**

| 处置 | 适用范围 | 做法 | 处数 |
|---|---|---|---:|
| **P1 注入点化** | `DATA`：`chart_spec` 3 处 + `structured_writer` 1 处 | 代码改 `paths.data_root()`；测试把 `monkeypatch.setattr(X,'DATA',tmp)` 换成 `paths.configure_data_root(tmp)`（用 `monkeypatch` 兜回原值） | **4** |
| **P2 改指 core** | `timing.stamp` 3、`historical_research.prepare_history` 2、`structured_writer.invoke_numbered_writer` 1、`historical_reader.HistoricalReader` 1、`reviewers.payload_for` 1、`historical_web.request` 1 | 测试改 `monkeypatch.setattr(core.X,'attr',v)`；**`app.X` 保留同名别名以免其它测试断** | **9** |
| **P3 改 patch 消费方** | `MODEL_*` 共 13：`model_client` 9（3 站点 × 3 名）+ `historical_web` 2 + `usage` 2 | 把 `MODEL_*` 收拢成 `paths.model_config()`，测试 patch **配置对象**而不是模块全局 | **13** |

> 分项合计 4 + 9 + 13 = **26**，与上表逐模块合计一致。

> **纪律**：这 26 处改动**必须逐条列进包报告**，并在 `G-S8-PATCH` 里留负向探针
> （先证明「patch 壳不再生效」，再证明「patch core 生效」）。不许"跑了全绿就算过"。

## 5. 建议顺序：先搬这 5 个最安全

**筛选判据（5 条全满足才算"最安全"）**：① 闭包内依赖 = 0（无层间耦合）；② 无 import 期注册表读取；
③ 无客户业务词；④ 不参与 spawn 子进程；⑤ 无 `DATA`/`ROOT`/`PACKAGE_DIR`/`MODEL_*` 全局。

| 序 | 模块 | 行 | 命中 | 为什么它是安全的 |
|---:|---|---:|---|---|
| **1** | `ooxml` | 2 | **已是 core 的壳**：`from core.tools.ooxml import W,S,UnreadableDocument,_col_index,read_docx,read_xlsx`。所谓"迁移"只是确认壳完整 | 零风险。`tests/test_s7_decoupling.py::test_ooxml_and_compare_reexport_identity` 已经在钉它 |

| **5** | `timing` | 55 | 闭包内**零依赖**；纯 stdlib | 唯一成本是 **3 处 `timing.stamp` patch 改指**（P2 处置）——把它放在第 5 位正好用**最小的 patch 面**先跑通 §4.3 的处置流程 |

**为什么是这 5 个而不是别的**：

- 它们**全部在 L0**，互相之间**没有任何依赖边** → 可以任意顺序、任意子集，**每搬一个都能独立验证**。
- 它们**没有一个是 import 期读注册表的 5 个模块**（`agent`/`chart_spec`/`style_skill`/`tool`/`writer_tools`）
  → 首 5 个**完全绕开** §4.1 的导入纪律风险。
- 它们**没有一个踩客户业务词** → 首 5 个**完全绕开** §0.4 的硬阻塞（B 类数据债可以并行去还，不挡路）。
- 它们**没有一个参与 spawn** → 首 5 个把 RISK-1 推到 L2 再解决，先拿到"搬家流程本身是对的"的证据。
- **累计 487 行**（2+121+120+189+55），**改动 ≈ 20 行**（4 个新壳 × ~4 行 + 3 处 patch 改指；`ooxml` 的壳 S7 已存在），
  改动/搬迁比 **≈ 4%** —— 这是整条路线里最优的"用最小改动验证机制"的入口。

> **紧随其后的第 6、7 个**：`structured_template`(266) 与 `event_analysis`(327)。
> `structured_template` 只惰性依赖 `chart_spec`（L1），所以必须先搬 L1 的 `chart_spec` 才能动它；
> `event_analysis` 在 SCC 里，必须等 L3 整批。**这两个不放进首 5 个，正是因为它们分别被层序和 SCC 咬住。**
