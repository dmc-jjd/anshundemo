**三条由此得出的硬事实**：

1. **函数内 import 是"防环"的刻意设计**，不是随手写的。`app/workflow.py:61` 在 `build_writing_graph` 里 `from .reviewers import …`、`main.py` 里 7 处延迟取 `reviewers`，都是为了**打破 `workflow ↔ reviewers` 与 `main → 一切` 的顶层循环**。**任何下沉动作若把这些改成模块顶层 import，会立刻造出 import cycle**（RISK-10）。
2. **`.reviewers` 是被 `main.py` 引用最多的模块（7 次）**，而它正是 S6 要"抽为基座通用模式"的对象。所以 S6 改 `core/graph` 时，`reviewers.py` 的**公开名字一个都不许变**（`ACTIVE_PHASES`、`review_ready`、`resolve_human_review`、`active_issues`、`after_human_change` 五个名字被 `main.py` 直接消费）。
3. **56 个函数里 20 个完全没有函数内 import**——它们只依赖模块级 6 个名字（`store`/`deps`/`app`/`UPLOADS`/`DATA`/`HTTPException` 等）与 7 个顶层 import 符号。这批是下沉时最安全的，**也是唯一能不动注入面的那批**（§0.6）。

### 0.3 `workflow.py` 三个图构建器的节点/边现状（`get_graph()` 实测 dump）

**`build_report_graph`（report）—— 6 节点 / 8 边，2 个条件边**

```text
EDGES
  __start__          -> validate_input
  validate_input     -> __end__            [cond]   (entry: 'process'|'stop')
  validate_input     -> data_processing    [cond]
  data_processing    -> event_analysis     [cond]   (after_processing: 'analyse'|'finish')
  data_processing    -> await_data_review  [cond]

```

**`build_writing_graph`（writing）—— 13 节点 / 21 边，3 组条件边、`revise_draft` 有 6 个出边**

```text
NODES  __start__, validate_input, write_draft, local_validation, style_detection,

       content_style_detection, final_format_review, await_final_review, __end__
```

**`build_template_graph`（template）—— 4 节点 / 3 边，0 个条件边（纯线性）**

```text
NODES  __start__, validate_input, local_compare_and_analysis, __end__
EDGES  __start__ -> validate_input -> local_compare_and_analysis -> __end__
```

> **关键事实**：模板图**没有任何条件边**，它的"行为"全在 `run_template()`（`workflow.py:279-353`，75 行）里，不在拓扑里。
> 因此 S6 对模板图只需**结构等价**（节点/边集合相等），不需要行为摘要——**别把力气花在它身上**。

**与 `core/ports.GraphSpec` 的表达力差距（这是 S6 的核心设计冲突）**

| 现状需要 | `GraphSpec` 能给 | 结论 |
|---|---|---|
| 节点 id | `GraphNode.id` | ✅ |
| 节点种类 | `GraphNode.kind: Literal['agent','tool','gate','loop']` | ⚠️ 现状 13 个节点里 `local_validation`/`style_detection`/`await_final_review` 既不是 agent 也不是 tool（是本地函数），`revise_draft` 是 agent，`format_review`/`content_review` 是 agent。**`kind` 只有 4 个值，装不下 6 种真实节点** |
| 静态边 | `GraphNode.next: tuple[str,...]` | ✅ |
| **条件边的谓词与结果枚举** | **无法表达** | ❌ **决定性缺口**。`format_route` 返回 'content'/'revise'/'finish'；`after_revision` 返回 6 个值之一 |
| 节点→动作绑定 | `GraphNode.ref: str`（只存名字） | ⚠️ 现状是**闭包**（`lambda tid: _process_records(dependencies,tid)`），名字 → 可调用对象必须另有注册表 |
| 图入口 | `GraphSpec.entry` | ⚠️ 现状用 `add_edge(START, …)`，且 `validate_input` 的出边按 `review_only` 变化（`workflow.py:82`）——**同一张图有两种入口分支** |

> 所以**不能**把 `GraphSpec` 当唯一真相。S6 的定稿方案是「**声明 + 策略注册表**」两段式，见 §4.1。

#### 判据的四分量（每个场景各算一组，另加总哈希）

| 分量 | 取值来源 | 抓什么 |
|---|---|---|
| **ORDER** | `store.events(tid)` 中 `type=='graph_node' and status=='started'` 的 `(graph, node)` 序列 | 节点顺序 / 是否走了条件边 / 循环跑了几圈 |

#### canon / scrub 口径（**四参数固定，改任一即"有意变更门禁"**）

```python
# 规范化
canon(o) = sha256(json.dumps(scrub(o), ensure_ascii=False, sort_keys=True,
                             separators=(',', ':'), default=str).encode()).hexdigest()
# 扰动清洗（递归；只看"整串恰好是 32/64 位小写 hex"的字符串）
scrub(o): str 且 ^[0-9a-f]{32}$ -> '<uuid32>'
          str 且 ^[0-9a-f]{64}$ -> '<hex64>'
          dict -> 按键排序后逐值 scrub；list -> 逐项 scrub；其余原样
```

**为什么必须 scrub**：`workflow.py:380/392/370` 的 `DraftVersion(id=uuid.uuid4().hex, …)`、`FactSnapshot(id=uuid.uuid4().hex, …)`、以及 `reviewers.py:210/213` 的 `review_item['id']=uuid.uuid4().hex` 是**每次运行都不同**的；
`content_hash` 又是"对含 uuid 的 payload 再做 sha256"，必然跟着漂。清洗掉这两类 hex，**恰好只去掉易变噪声，保留全部语义字段**（实测两次运行 15/15 相等即为证据）。

**为什么必须 `freeze()` 输入**：§0.8 实测。`freeze(data)` = 逐条目重建 zip，`date_time=(2020,1,1,0,0,0)`、`compress_type=ZIP_DEFLATED`。
**不冻结 = 摘要随运行时刻漂移 = 门禁永远红灯**（而且红得莫名其妙）。

## 4. 必须回答的四个设计问题

### 4.1 `GraphSpec` 表达不了条件边，怎么办？（**S6 的核心设计冲突**）

先给结论：**不扩展 `core/ports.py`（S1 冻结），改用「声明 + 策略注册表」两段式**。

| 方案 | 内容 | 判定 |
|---|---|---|
| (a) 扩展 `GraphSpec`（加 `edges`/`conditions` 字段） | 一次到位 | ❌ **破坏 S1 冻结**；且 `GraphSpec.validate()` 的语义要重写，`test_ports_contract.py` 14 个用例会红 |
| (b) 把条件谓词塞进 `GraphNode.ref`（字符串，如 `"format_route:content"`） | 不扩字段 | ❌ 把可执行逻辑编码进字符串，**不可静态校验**，且 `ref` 的语义是"agent role_id / tool name / gate id"（`core/ports.py:203` 注释），不是"表达式" |
| **(c) 声明 + 注册表（本方案）** | `GraphSpec` 只声明**节点 + 静态边 + entry**；条件边由 `compile_graph(..., edges=…)` 的参数传入，键是 `(node_id) → (router, {outcome: target})` | ✅ **零改动 `core/ports.py`**；`GraphSpec.validate()` 的 `dangling_edge` 检查仍然有效（它检查的是 `GraphNode.next`）；条件边的悬空由编译器额外校验 |

**为什么 (c) 是诚实的**：`GraphSpec` 从 S1 起就只声明"能静态知道的"（节点、静态边、入口），
而**条件分支本来就不可静态枚举**——它的 outcome 是由 `format_route` 这类函数在运行期算的。
硬塞进声明 = 把运行期逻辑伪装成数据。**两段式把"静态结构"和"运行期决策"分开，正好对应 §1 的 ORDER（结构）与 CALLS（决策）两个分量。**

**代价（必须写进 handoff）**：本阶段之后 `workflow.py` 的"图"真相有**两个家**：`GraphSpec`（结构）+ `edges` 注册表（决策）。
这比现状（一个函数里全都有）分散，但换到了**可静态校验 + 可复用**——这正是 P6 "抽为基座通用模式"的内容。

### 4.2 审校循环抽成"通用模式"，到底通用在哪？

**通用的部分**（进 `core/graph/review_loop.py`）：
`「N 个审校角色 → 每个角色有独立预算 → 可退修则回到校验链、不可退修则转下一阶段 → 最后一轮只审不退修」`这个**拓扑形状**。

**不通用、必须留在 `app/` 的部分**（这里最容易过度抽象）：

| 留在 `app/` | 为什么不能进 core |
|---|---|
| `format_route` / `review_route` / `after_revision` 的**判定逻辑** | 它们读 `state.metadata['writing_review_run']`、`repairable(...)`、`active_issues(...)`——**全是 `app/` 的数据结构**；搬走就是把 `app.state` 的 schema 也搬进 core |
| `ROLES=('format_reviewer','content_reviewer')` 的**具体名字** | 名字是客户包提示词包的键（`format_reviewer.review`），属客户面 |
| 预算 **5** | 现状是字面 5；`ReviewerSpec.max_rounds` 是未被消费的 2（§0.7 F8）。**显式传入 5，不许用 dataclass 默认值** |

> **判据**：抽完之后 `reviewers.py` **0 行改动**。若抽"通用模式"需要动 `reviewers.py`，
> 说明抽错了对象（抽的是判定逻辑而不是拓扑形状）——**退回去重抽**。

### 4.3 `main.py` 拆到什么粒度算完成？（**任务书要求明确回答**）

**结论：本阶段「不拆 router 文件」；`main.py` 保留全部 52 个装饰器，把领域组装下沉为纯函数。**

完成 = **同时满足下面 5 条可机械判定的判据**（全部能用 `ast`/`app.openapi()` 检查，不靠肉眼）：

| # | 判据 | 判定方式 | 现状 |
|---|---|---|---|
| **C1** | `app.openapi()` 规范化摘要与 S6 前**逐字符相等** | `gate_openapi.py` | 基线待录（F6：现在压根没有） |

**为什么不是"按域拆成 6 个 router 文件"**——三条实测理由，前两条是决定性的：

1. **注入面会碎**（§0.6）：15 个测试文件靠 `monkeypatch.setattr(main,'store'…)` 工作，现行代码之所以有效，是因为**路由函数体在运行期按模块全局解析**这些名字。搬进 router 后

   要保住就得 52 处逐处写 `from app import main as _m; _m.store…`，把"模块常量"降级为"运行期属性查找"——**那是行为变更，不是纯搬迁**，违反 §7 Ponytail 第 1 条。
2. **收益与计划的 P6 目标无关**：P6 说的是"`main.py` **收拢为通用任务生命周期路由**"——收拢的对象是**职责**（路由函数变薄），不是**文件个数**。

3. **拆文件是纯机械变换，任何时候都能做**；而它的**前置条件**（G-OPENAPI + G-INJECT）恰好是本阶段 A/D 包的产物。
