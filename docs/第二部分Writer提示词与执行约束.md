# 第二部分 Writer：从本月处置建议改为有依据的风险研判

本轮前瞻窗口由用户明确为2026年11—12月。模型先用知识比较至少4类候选，复用已有资料，按缺口联网核实，再从历史、季节或已核实地方活动中混合选择3—4类。可执行提示词统一位于 `app/agent.py`；Schema与程序校验位于 `app/section_two.py`，研究编排位于 `app/historical_research.py`。维护方法见[Agent提示词维护说明](Agent提示词维护说明.md)。

## （一）研判分析

300—500字，交代少量当前事实，重点展开两条不同的风险链：

**尚未化解的具体条件 → 升级过程 → 影响对象与后果 → 可观察信号 → 对应主体的实质阻断措施。**

不能只把“程序质疑变为情绪”“发生事件后影响形象”当作分析。必须解释风险转化的环节，例如责任认定、权益处理、证据反差、办理进展与重复诉求怎样相互作用。建议要切断上述链条，不能仅以宣传、统一口径、及时回应充当措施。

模型返回 `analysis_plan`：自然语言正文、概述及两条风险链。结构作为审计依据，正文由Writer自然成文，程序校验来源和300—500字限制；不强迫模型把零碎字段机械拼接。投诉、爆料保留归因，条件推断不写成已发生事实；司法程序事项不预设违法结论或安排未经依据的机构干预裁判。

## （二）工作建议

严格选择 **3—4类事件风险**，面向未来1—2个月，每类一段：

1. 准确说明依据：历史案例/复现，季节条件，或经核实的地方活动背景。
2. 未来窗口的具体触发条件。
3. 风险如何演变，可能影响谁、造成什么后果。
4. 哪些早期信号值得跟踪。
5. 哪些主体应采取什么前置措施，以及措施要阻断什么风险。

每条建议约250—400字，最高600字。模型返回 `outlook_items`，每项必须有paragraph完整自然段，与审计字段对应，程序校验并自动编号。保留机制和针对性，不能省略正文后机械拼接审计字段；不因无关的字段前缀或小幅字数分配差异转人工。

不得沿用本月TOP10逐条写处置建议；不得以信息量峰值、属地不明等统计或数据质量项代替事件类别；不得把单日信息量高推断为事件风险高，也不能从属地未知推断基层推诿。

历史依据中的年份、数字必须对应实际引用的有效资料，不能混用被剔除的候选。风险链不用箭头或清单符号；不承诺零事故、零欠薪，不自行制定无来源的响应硬指标和发生概率。

## 联网与依据强度

模型知识可用于候选比较及明确条件的季节推演。具体地方事实不确定时使用实际 DeepSeek Search/Fetch 核实，优先近3年、最多5年；历史案例月份须对应未来窗口，季节/活动背景材料不强制同月份，但不得冒充同期事实。资料不得晚于报告截止日。不同年份、发布日期与发生日期、安顺与外地、事故与季节提醒都需区分。

- 官方明确提示本地同期高发的，可作为定性高发依据，不能当作发生次数。
- 跨年本地同期记录可以证明复现，不等于完整的全市高频统计。
- 单个案例可作案例参考；季节提醒可支持条件性风险，不冒充本地历史高频。
- 网页必须实际阅读；引用由程序按已读URL绑定。原文摘录用程序提取的连续片段，避免模型重打、改写或拼接证据。

搜索阅读结果、出处、年份和被剔除原因保存为工件，在报告预览中可以查看。搜读按成功请求另计费用，并纳入任务费用展示，价格可配置；模型Token另行计量。

## 执行与人工兜底

每批模型生成最多三轮纠错；工具调用预算结束时强制总结已读材料，避免丢弃证据或一直搜索。先完成至少4类候选比较，再形成3—4类有依据的未来风险；不足时可补充季节条件或核实地方活动，不要求全是历史高发，也不用本月事件清单凑数。

升级提示词只使第二部分的旧机器稿失效；第一部分、图表口径、事件归并和分类的人工判断保持。已经人工修订的文字不再交回模型；人工补填后只做本地保存与格式校验，直接进入下一个节点。
