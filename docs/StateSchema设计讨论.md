# State Schema 设计建议（讨论稿）

建议增加 `app/state.py` 统一定义各阶段交接的数据结构、必填字段和流转校验。它存放 Python 类型与约束，不存放每次运行的业务数据。

运行数据建议写入 `data/states/<task_id>/<stage>-<revision>.json`，或保留现有不可变工件存储并增加按阶段组织的索引。每个快照记录任务 ID、阶段、修订、输入快照引用、模板版本、源文件哈希、产出引用、机器待处理项和人工不确定项。大工作簿、向量、成员清单和正文通过工件引用关联，避免每次传完整数据。

建议阶段契约：

| 阶段 | 必须提供 |
| --- | --- |
| 模板确认 | 两份来源哈希、比对引用、确认版本、字段 Schema、统计与 TOP10 规则 |
| 数据导入 | 文件引用、明细表、记录工件、原始行数、字段映射 |
| 本地归并 | 记录引用、向量版本、阈值、组代表、成员、边界候选 |
| 模型研判 | 每个候选的明确判断、理由；网络或格式失败单独列为机器待处理 |
| 事件分类 | 每个最终事件的类别、判断来源；人工不确定必须有模型理由 |
| TOP10 | 负面且预警范围、事件成员指纹、排序计数、梗概、来源引用 |
| 数据确认 | 已解决的人工项、锁定结果引用、版本哈希 |
| Writer | 确认模板、锁定事实、字段清单、可用证据与当前输出 Schema |

每个阶段只接收相应 State，入口校验必填字段，出口校验成员覆盖、数量一致和来源合法。禁止依赖 Agent 从散落的日志或提示词中猜测路径、范围和版本。

当前已有通用 `TaskState` 和不可变工件，但 `metadata` 是宽泛字典，细分阶段约束不足。本轮事件处理已先采用 Pydantic 响应结构、精确批次覆盖校验和可恢复检查点；尚未将全系统统一迁移到 `state.py`，以保留本项作为设计讨论。
