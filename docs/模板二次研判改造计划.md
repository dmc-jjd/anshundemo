# 模板生成二次研判改造计划

本计划基于当前 `workflow.run_template`、`structured_template.build_structured_template`、模板确认 API 和可视化页面核查。用户给出的四项核心差距属实。现有成功日志只能证明模型请求返回过合法摘要，不能证明模型审定过模板结构。

本文件最初为改造计划。2026-11-07用户确认方案并要求同时支持多份报告后，已实施输入契约、完整语义研判、编译校验、确认门禁和多报告页面；真实运行与验收进度见项目 progress.md。此前事件研判、分类和TOP10续作独立验证。

## 目标流程

两份历史 Word → 本地提取与对齐 → 本地结构假设 → 模板制定规则＋两份可提取原文＋本地假设 → 大模型结构化二次研判 → 程序校验与编译新候选 → 可视化人工确认 → 不可变模板版本 → 数据处理与 Writer。

本地比对是预处理，不再直接决定最终字段。模型研判必须实际参与候选形成；请求失败、输出不完整或程序校验失败时不能进入人工确认。有效模型研判中仍无法确定的业务项，才可以交人处理。

## 1. 规则与阶段契约

模板制定规则包含：

- 固定文字与动态内容如何区分。两份原文相同只作为证据，不能据此固定报告年月、发布日期或相同的历史事件。
- 统计数据、时间字段、分类、原文引用、分析文字、重复列表、表格和图表的位置及所有权。数字由工具取数，文字由 Writer 填写。
- 一个语义单元形成一个字段；完整事件示例、媒体清单和主题列表不能被字符串相同碎片切成零散小槽位。
- 每个字段必须有显示名称、语义、来源要求、统计单位、时间范围、格式、缺失策略及对应原文位置。人看显示名称和正文预览，Agent 看完整定义。
- 已确认 TOP10：负面且已预警的记录，按具体事件去重，再按每个事件内符合条件的记录条数降序；一个事件一行，使用严肃简明梗概。模型不能擅自改成原始标题、全部记录数量或没有依据的热度分数。
- 未确认的其他业务范围保留为未决项，不强行从历史相同数字推断。统计范围不全局混同。

`state.py` 先定义 `TemplateModelInput`、`TemplateReviewResult`、`TemplateCandidateState`。运行数据继续使用现有不可变工件，增加阶段快照索引；代码定义不混装运行数据。后续再逐步覆盖其他阶段，避免一次迁移全系统。

## 2. 发给模型的内容

输入包至少包含：

1. `policy`：规则版本、规则内容、已确认业务定义、明确未确认的口径。
2. `source_reports[]`：文档 ID、SHA-256、完整可提取正文与表格、稳定块 ID。嵌入图表另标位置与提取状态，不把未读取的图片内容伪装成已读。
3. `local_comparison`：对齐关系、差异位置和未对齐段落。
4. `local_hypothesis`：本地固定文字与字段假设，注明只是待研判假设。
5. `available_bindings`：实际支持的工具字段、时间参数和格式操作；模型只能从目录中提出数据绑定，不能编造工具路径。
6. `output_contract`：结构化输出约束，包含覆盖范围与来源校验规则。

按来源报告和段落记录输入覆盖，保存不含密钥的输入快照、哈希和字符数/token 使用。上下文过长时按完整小节拆分，并保留全篇目录与跨节校验，不能悄悄取前几段冒充全文。

## 3. 模型必须产出的结构

`TemplateReviewResult` 包含：

- `source_ids`、`policy_version`、`local_hypothesis_hash`：明确审查对象。
- `block_decisions[]`：每个正文/表格块的结构判定，含固定文本、动态字段、重复结构或未决项。
- `field_decisions[]`：接受、修改、合并、拆分或新增字段；包含完整语义区域及各报告对应的原文位置、判定理由。
- `business_rule_findings[]`：哪些口径符合规则、哪些历史数字或措辞存在冲突，不能由模型擅自更改已确认业务规则。
- `unresolved_items[]`：只有证据或业务定义确实不足的项，附具体原文和需要人决定的内容。
- `review_summary`：便于页面呈现的简短说明，不能代替上述判定。

程序负责验证来源位置与原文一致、块覆盖完整、字段 ID 无冲突、无非授权业务规则改写、数据绑定存在。模型可以提出新语义字段，但必须具有来源，不能自由拼接未经校验的 Word XML 或任意 JSON Patch。

校验通过后编译新的候选及其 Writer/完整输出 Schema。本地原候选、模型结果和编译后候选分别留存；不直接覆盖原始 Word。Schema 由程序生成，模型对结构的判断真正影响编译结果。

## 4. 状态流转与确认接口

建议状态：

`template_parsing → template_local_ready → template_model_reviewing → template_review_validated → awaiting_template_confirmation → template_confirmed`

模型请求失败进入 `template_model_review_failed`；来源、覆盖或结构校验失败进入 `template_review_validation_failed`，允许重试/有限纠正，但不能转为人工确认。成功请求但只返回摘要，也视为结构不完整，不能通过。

确认 API 同时校验：已验证的模型研判引用、最终候选哈希、任务修订号、规则版本、未决项的真实处理结果。API 直接调用同样不能绕过。不能再跳过 `template_candidate` 阻塞项，也不能通过一个“已阅读”布尔值替代实质未决项处理。

已确认模板不可变。规则、源报告或结构发生变化时生成新候选与新研判记录，旧模型结论不得套用到新版本。旧流程候选标注为尚未完成结构研判，需重新研判后确认；已有历史版本保留来源和实际状态，不补造成功记录。

## 5. 人工页面

主视图仍是直观报告模板：固定正文＋具名动态标签＋表格/图表位置。提供“本地初稿 / 模型研判后”对比和“两份原文”切换。

点击标签显示其含义、数据来源、展示格式、模型为什么这样划分，以及对应原文。模型已确定的修正合入候选供整体确认；仅真正未决项展示操作入口。失败状态显示重试和具体失败阶段，不显示可用的模板确认按钮。

人确认的是修正后的整个模板版本及业务未决项，不要求逐个阅读底层 JSON 或强制点击每个确定字段。确认动作绑定实际预览的候选哈希，防止后台更新后确认到另一份内容。

## 6. 验收条件

- 模型请求包缺少规则或任何一份原文，入口校验失败。
- 本地误将年月、重复历史案例固定，模拟模型改判后，最终候选和 Word 预览确实随之变化。
- 只返回 `summary/source_files`、漏块、伪造来源、无效绑定、非法 JSON 或超时均不能进入人工确认。
- 有效研判中的真实业务冲突可以进入人工，但不处理完不能确认。
- 直接调用确认 API、使用旧修订/哈希或修改规则后复用旧研判，均被拒绝。
- 重试复用本地解析结果；确认后 Writer 读取编译后的模板和 Schema，不退回本地初稿。
- 真实 6/7 月报告完成一次全链路；保留原文、输入包、结构化判定、候选变化、校验报告、页面证据。10 月报告继续留作独立报告生成验收材料。

## 多份报告的范围

按用户新增要求，已同时将上传、对齐、来源校验和模板加载统一扩展到N≥2，输入包采用 `source_reports[]`。第一份作为排版基准，全部报告参与语义研判；6/7/8月三份样本执行真实测试。

多份报告的一致性可增强证据，但不能用多数票自动把年月、事件标题或相同数值判为固定文字。多报告支持不是修复“模型没有参与结构决策”的替代方案。
